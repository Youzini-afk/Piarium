## 要实现的体验

用户可以配置一种通用的“快速决策模型”。首个后端是 Jev，以后可以接同类模型。这项能力判断已有材料、候选和具体动作，不属于普通聊天模型，也不局限于重排。

主 Agent 仍通过一次自然语言 `explore` 调用发起检索。系统先找到并读取代码，再判断哪些材料值得保留、哪些线索值得继续查。根据实际代码展开定义、引用、调用关系、导入或目录大纲，取得新材料后继续选择，最终返回互补的真实源码与来源。

特别注意：三行转发代码可能不值得直接返回，却是追到真正实现的关键入口。**返回价值和继续探索的价值必须分开。**

本阶段同时交付通用能力和这个真实消费者。Computer Use、其他工具/技能路由留作后续，不扩展成本次交付。

## F0：能力、配置和入口

- 在现有 protocol / application-client / Host / pi-host 边界内定义供应商无关的选择、判断、评分请求与能力描述。只实现真实消费者需要的操作，保留正常扩展空间，不先搭通用 DSL。
- 产品名称统一“快速决策模型”；代码沿设计使用 `fastDecision` / `FastDecisionModel`。Jev 的原生 primitives 留在 adapter 内，不要求所有模型都具有相同形状。
- 接入独立配置种类，设计名为 `harness.fastDecision`：通用默认、已注册用途覆盖、显式关闭。用途覆盖优先于默认；关闭不能被默认重新开启。
- 复用现有用户/operator 设置与 Pi 凭据 owner。Host 只解析去凭据绑定，通过现有 broker / Pi 后台推理通路调用；不能借第一个活动聊天或主 Agent 的模型、身份与凭据。
- 同一次 query 固定开始时的模型绑定；设置变更影响下一次 query。凭据撤销与访问撤销仍遵守既有实时失效规则。
- 设置页在模型分工附近提供实际可用入口、能力说明和状态，并接齐共用设置目录、`settings_search/read/update` 与相关 i18n。UI 与 Agent 修改同一个 owner，不能出现“界面保存了但运行端没消费”的配置。
- 未配置时原检索正常可用。配置有效且支持当前用途后，正式参与判断，不另加实验开关。

## F1：真实推理通路与 Jev 适配

先核对 TypeSafe 当前官方文档与请求示例。现有设计依据为 `systemone` 及 Choice / Noul / Score；**实施时重新确认 endpoint、认证、字段、返回映射、模型版本、模态和实际容量**，不要凭普通聊天 API 的习惯猜请求。

官方入口：

- https://docs.typesafe.ai/introduction
- https://docs.typesafe.ai/models
- https://docs.typesafe.ai/primitives/choice
- https://docs.typesafe.ai/cookbooks/function_calling
- https://docs.typesafe.ai/cookbooks/semantic_find

实现要求：

- 复用 pi-host 后台 inference / broker 以及 Pi AuthStorage；需要新增 provider 时接入原有凭据与管理通路，不在 Host、renderer 或检索模块复制密钥库。
- adapter 接收目标、实际材料、问题/候选身份与取消信号，返回能关联回本次请求的结果。消费者依赖能力，不依赖 Jev 专有响应结构。
- 支持当前使用需要的批处理与容量处理。供应商限制留在 adapter；超过真实容量时拆分材料或分层选择，并如实保留未评估状态。
- 区分相对分布、评分和独立概率。缺结果不能变成 false 或零分，最高排名不等于候选确实有用；不编造置信度、用量或耗时。
- 允许“没有合适候选”。非法 ID、部分返回、格式错误、供应商失败与取消均应保留真实含义，不能被包装成一次成功的低相关性判断。
- Jev 当前设计用途是给定候选的判断。新检索词由现有生成式能力或源码中实际发现的符号/字面量提供；不要要求 Jev写自由文本，也不要靠连续字符选择伪造生成能力。
- 生产代码必须发真实协议请求。定向验证可以使用符合官方协议的本地 provider 替身；不能把生产实现写成假响应，也不需要真实付费账户往返才继续做消费者。

## F2：把选材接进公开 explore

从公开工具追到 `explore.query.*` 与其生产装配，再插入新能力。优先检查这些入口及其实际消费者：

- `packages/pi-host/src/harness/explore-tool.ts`、`explore-model.ts`
- `packages/web/application-host/lib/harness/explore-query-services.ts`、`explore.ts`、`explore-rerank.ts`
- `packages/web/application-host/lib/knowledge/semantic/workspace-runtime.ts`
- `packages/pi-host/src/session-host.ts` 与后台 inference runtime

具体要求：

- 给模型的是当前 query 已授权、带来源身份的实际正文，不是只凭路径、文件名或摘要猜材料价值。
- 模型输入组织在最终展示裁剪之前；不要把给主 Agent 的短预览直接当作完整评估材料。评估不了的范围如实保留状态。
- 选材考虑已选材料、重复内容与新增贡献，避免一组相似高分片段挤掉另一条关键链路。
- 快速决策负责适用的选材/动作判断；`models.explore` 仍按需生成搜索表达。已经由快速决策处理的同一项判断，不再串一次 LLM 选材或普通 rerank。
- 未配置或不具备所需能力时沿现有检索路径。调用失败时保留已读材料和可用来源顺序，清楚表达失败；不自动换另一个付费模型接盘。
- 删除被替代消费者中重复的语义评分，不再用旧的文件名奖金或关键词猜测覆盖模型选择。保留词法、向量、结构召回和无模型检索的独立能力。

## F3：同一查询内逐步探索

这里需要真实的“看过代码后再决定下一步”，不能只是给首次召回结果排个序，或把旧的一轮补搜改个名字。

- 在现有 query owner 中管理已读材料、待执行动作、已执行身份与来源修订。复用原 queryId、范围、工作预算、取消、输出存储和句柄，不另建查询引擎、数据库或常驻子线程。
- 候选动作从当前真实材料产生：读取函数/容器/相邻条件块，查定义/引用/调用实现，沿导入、事件或服务连接追另一端，展开目录/大纲，搜索已发现的确切符号或字面量。
- 动作绑定完整目标、依据与来源身份。模型选择本次候选的 action ID，原服务负责授权和执行；不能让模型拼出任意路径、参数或自称存在的代码关系。
- 执行后将新正文和新线索增量纳入判断。支持独立方向并行，也能回到尚未执行的备选；不要只沿一个目录分支走到底或一次展开全部出边。
- 独立材料成批判断。精确路径/对象可以直达，不给简单查找强加前置模型调用，也不每到一条结果就请求一次模型。
- 入口不足时，利用目录、大纲、签名、已有说明或已配置的生成式规划补充线索。不预先生成全仓摘要，不因目录低分永久排除子树。
- 对转发桥接、重名符号、事件及服务连接检查实际原文。共现不当作已确认的调用；暂无线索不当作仓库没有实现。
- 按动作身份、参数与来源修订去重；没有新材料或新动作时不反复评价同一状态。取消/结束后的迟到响应不能复活查询，旧修订判断不能覆盖新材料。
- 结束依据沿既有预算与真实进展：目标已取得、无值得执行的新动作、无新增材料、取消或预算结束。模型的“够了”只适用于已读材料；未完成来源仍需披露。
- 不新增统一的文件数、深度、轮数、调用数、并发数或置信度硬门槛。实际平台容量按依据处理，工作预算沿现有可配置机制。
- 最终返回当前源码、路径、行范围和实际缺口。决策详情进入已有 query provenance，不把每轮中间判断全部塞回主 Agent 上下文。

## F4：完整性与适量验证

验收首先看功能和调用链。不要用测试总数、文件数量或合法的 typed 输出证明“逐步探索已完成”。也不要为这一阶段建设评测平台、全平台验证流程或长期 CI 门禁。

沿已有装配选择能够暴露真实问题的定向场景，例如：

- 配置默认/覆盖/关闭，在 UI、Agent 设置工具和生产 query 中得到一致结果。
- 一次公开 `explore` 请求先找到薄的转发入口，模型选择继续追踪，原服务读取到更深实现，再返回真实源码。
- 同一问题存在多个独立方向时能保留互补材料，重复片段不占满结果；低返回价值的片段仍可成为探索入口。
- 取消、修订变化、非法候选或部分返回不会串入别的查询；失败后已有源码仍可用，未配置时原流程可用。

这些是应覆盖的重要行为，不是固定测试清单或数量要求。优先复用现有测试和少量本地复现；需要 provider 替身时，只替换外部模型边界，查询编排、读取和结果返回仍走生产实现。不要直接伪造最终文件清单来证明动态探索。

运行与实际改动相称的类型检查、lint 和定向验证。协议/公共类型改动要覆盖真实消费者，避免旧 dist 掩盖类型或构建问题；若新增生产依赖，正确声明运行时归属并更新涉及的锁文件，不顺带升级整仓依赖。

真实外部登录、付费模型调用、跨平台 Surface、完整桌面重启和全量端到端实测不作为本轮完成前提。没有做过的速度、中文问题效果、长输入表现或跨平台运行如实记录，不声称比其他产品更快、更准。

## 实施与交付方式

自主推进常规实现选择；F0–F4 是同一交付目标中的工作切片，不需要每完成一个切片就等用户确认。可按依赖拆分工作，但共享协议、配置语义和 query 状态必须有清楚的整合责任，避免不同执行者各建一条链。

完成后同步设计与 plan 中实际调整的地方、status 中交付事实、所属模块文档，以及必要的 architecture / roadmap 引用。未实现、已接线未实测和已验证要分清楚，不复制多张容易漂移的状态表。

按仓库规则进行目的清楚的提交与推送，沿用用户作者身份，不添加 Agent/助手署名。不要改动已有发布标签或发新版本，不把 kernel 二进制、manifest 或本地 Host 数据目录等临时生成物顺手入库。

最终报告需要让接手验收的人直接定位实现：

1. 提交、推送与工作区状态。
2. 用户怎么配置，主 Agent 怎么自然使用；未配置与失败时的实际行为。
3. “设置 → 后台推理/adapter → query 选材 → 下一步动作 → 真实读取 → 最终源码”的关键文件与调用关系。
4. 逐步探索实际做到哪一步，旧的哪些重复路径已删除或替换。
5. 做过的定向验证及其支持的结论，剩余未实现项和未实测项分别说明。

完成标准：快速决策模型是可配置、可复用的真实能力；Jev 适配与公开 `explore` 的选材、动态探索均已接线，用户可以实际使用；代码复用现有权限、文件、查询与推理 owner，没有用额外流程和重复系统换取表面完整。
