# Piarium 科研集群设计

Status: accepted product and architecture design; implementation not started

Last updated: 2026-09-19

本文定义 Piarium AI4S（AI for Science）方向的产品中心、研究集群协作形态和第一阶段实施边界。
它建立在现有 Piarium Agent Harness、Thread/Run、Rust kernel、检索、上下文和权限能力之上，不另建一套
Agent runtime、文件权威或持久化系统。当前交付状态仍以 [agent-harness-status.md](agent-harness-status.md)
为准；本文中的“应当”描述目标设计，不能当作已经接线。

## 1. 产品判断

科研工作的主要瓶颈不是把过程整理成足够多的记录，而是研究者能否更快地：

- 发现值得追查的问题；
- 建立跨文献、数据和代码的理解；
- 提出互相竞争的解释；
- 设计能够区分这些解释的行动；
- 把想法快速变成计算、模拟或数据分析；
- 从异常和负结果中发现下一轮问题；
- 形成能支撑结论和文章的整体论证。

证据、版本、运行记录和复现是保证判断不失真的手段。它们必须存在，但不应成为用户开始研究前必须维护的表单，也不应成为产品前台的中心。

Piarium 的科研方向因此定义为：

> **一个由异构模型和计算资源组成、能够并行发现问题、设计实验、快速执行并持续综合的科学研究集群。**

用户面对一条首席研究主线，主线按需要派生多个独立研究分支。强模型负责问题发现、第一性原理分析和综合判断；不同能力的模型负责文献调查、实验设计、实现、监查和复核；Host 调度模型和实际计算资源，Thread/Run 承载分支生命周期。

科研工作的严谨性沉到系统内部：真实输入、运行、输出、引用和版本自动留下可回看的来源。前台首先呈现研究路线、重要新现象、分支卡点和下一步投入方向。

## 2. 第一性原理

### 2.1 科研的基本循环

科研不是“填写计划、执行实验、提交报告”的固定流程，而是对不确定问题持续做有区分力的行动：

```text
问题或异常
  ↓
对现象的暂时理解
  ↓
多个可能解释
  ↓
能区分解释的观察、检索或实验
  ↓
真实执行与结果
  ↓
更新理解，派生下一轮问题
```

一个分支早就有新发现时可以立即派生下一步，另一个分支仍在准备环境，第三个分支可以暂停或转向。研究集群不等待一批任务全部结束后才综合。

### 2.2 AI 的优势与人的职责

模型的优势是同时阅读大量材料、从不同角度提出候选解释、快速生成实现和处理多条反馈。研究者掌握问题价值、领域目标、资源取舍和最终判断，也可以随时改变方向。

Piarium 不把模型的数量或排名当成科学证明。模型之间的独立意见用于扩大探索和暴露冲突；结论仍必须回到实际材料、运行和可解释的观察。

### 2.3 研究效率的定义

集群效率不是调用了多少 Agent，也不是并发数最大。它是单位时间和资源内带来了多少新的研究进展，包括：

- 找到新的问题或机制；
- 排除错误方向；
- 产生可重复的异常或结果；
- 形成更好的下一步实验；
- 让结论或文章论证前进。

没有必要启动 Agent 的批处理、编译、指标收集和进程监控由程序直接完成。模型只在需要理解、选择、改写或解释时介入。

## 3. 产品形态：一条主线与多条研究分支

### 3.1 首席研究主线

用户看到的是一条持续推进整体问题的主线。首席模型负责：

1. 把用户的模糊描述还原成待研究的问题和约束；
2. 发现不同的解释框架和相互竞争的假设；
3. 决定哪些方向值得并行探索；
4. 把分支结果放在一起寻找新关系、冲突和反例；
5. 决定继续、收缩、合并、升级模型或重新定义问题；
6. 形成当前结论、研究备忘录和文章主线。

首席模型不负责轮询进程、搬运每条日志或亲自实现所有代码。普通状态变化由调度器和 UI 处理，只有足以改变研究判断的新信息才唤醒它。

### 3.2 研究分支

一个分支代表一条独立的研究路线、解释、实验设计或实现路径。分支至少有：

- 目标：这条线要弄清或验证什么；
- 当前输入：用户材料、父分支结果和允许使用的来源；
- 工作上下文：模型、工具、权限、工作区和计算资源；
- 观察：新发现、结果、失败和未决问题；
- 下一步：继续、派生、等待、升级或结束。

这些字段由系统从实际工作中形成，默认不要求用户填写，也不要求每次工具调用都生成一条人工记录。分支向父线回传简短变化和可读取的原始材料引用，不能把完整对话灌入父上下文。

### 3.3 Thread 与 Run 的对应

沿用现有 Thread/Run 契约：

- **Thread** 是可以长期继续的研究分支，保留工作身份、成果和关系；
- **Run** 是该分支的一次具体推进，冻结本次模型、工具、权限、范围、输入来源和工作状态；
- 同一 Thread 可以从快速调查切换到强模型解释，再切换到实现或复核，而不丢失已有成果；
- 过期背景可以 fresh 重建输入，工作成果和历史引用继续保留；
- 文件变化、实验产物和分支结果通过现有 WorkingState/Integration 进入父线，普通消息不冒充代码同步。

Thread 树负责谁派发了谁、责任、取消、等待和资源归属。研究发现可以通过引用跨分支复用，不为研究知识再建一棵与执行树平行的强制图。

## 4. 异构模型与职责

模型槽位按能力配置，不能把产品逻辑永久绑定到某个型号。Astra、肥波、Sol、Opus、Flash 可以作为用户当前的候选绑定，但同一能力在不同 provider 下可以替换。

| 能力 | 典型职责 | 动态升级或改派条件 |
| --- | --- | --- |
| `frontier-reasoning` | 问题发现、第一性原理分析、跨分支综合、核心论证 | 分支冲突、重大异常、研究方向改变、文章论证缺口 |
| `deep-design` | 关键文献深读、机制解释、实验设计、混淆变量分析 | 理论冲突、实验成本高、结果难以解释 |
| `high-throughput-execution` | 实现代码、环境处理、批量分析、普通结果解读 | 重复失败、复杂算法、异常结果 |
| `fast-exploration` | 术语扩展、局部假设、反例、低成本变体、快速检索 | 局部结果影响主方向或需要深度综合 |
| `critical-review` | 独立复核关键实现、方法、异常优异结果和主张 | 只对高影响或有冲突的结果调用 |
| `scientific-writing` | 组织结果、维护候选贡献、暴露论证缺口 | 发现无法由现有结果支撑的主张 |

模型角色是默认路由，分支可以按结果升级、降级或更换模型。快模型不只做工人，也可以大量提出局部想法；强模型不只做主管，也可以直接参与关键实现。普通批处理和日志监查优先由程序完成，Flash 在异常解释和快速修复时介入。

## 5. 默认研究循环

一次研究推进按以下形态运行，不要求所有项目经过相同数量的阶段：

1. 用户给出问题、已有材料和可用资源，首席模型形成初始理解；
2. 按不同解释框架派生若干独立调查或设计分支；
3. 文献、代码、数据和轨迹调查持续为这些分支提供输入；
4. 分支设计低成本且区分力强的检查，执行组批量实现和运行；
5. 结果、异常、失败和冲突按实际事件回流，不等待全部分支结束；
6. 首席模型综合分支之间的新关系，淘汰、合并、升级或派生方向；
7. 研究写作线维护当前可表达的论点，发现论证缺口时重新派发调查或实验；
8. 用户随时可以改变目标、停止方向、扩大路线或要求集中综合。

### 5.1 动态矩阵

研究矩阵可以同时包含不同假设、机制、方法、条件和验证成本，但不一次展开全部组合。每个方向先获得能区分它与其他方向的低成本行动，再根据结果追加资源。

资源分配保留两类投入：

- 继续推进已经出现信号的方向；
- 保留尚未确定但具有独特解释力的方向，避免所有资源只追逐容易产生数字的路线。

代码实现失败不等于假设失败，低成本试验没有信号也不自动等于方向无价值。调度器向首席模型提供真实失败类型，避免把工程问题误判成科学反例。

## 6. 调度与资源协作

### 6.1 首席模型与 Host 调度器分工

首席模型决定研究优先级：哪个问题值得追、哪个结果改变了判断、下一步需要什么行动。Host 调度器决定执行时机：当前有哪些模型、CPU/GPU、数据和工作区资源，以及哪些任务需要排队、取消、合并或等待。

模型不负责反复查询进程状态，也不负责计算资源名额。调度器不替模型裁定科学价值。二者之间通过研究分支的目标、结果变化和资源要求协作。

### 6.2 事件触发综合

普通进度不唤醒首席模型。以下信息足以触发一次定向综合：

- 出现与当前假设不一致的观察；
- 多个分支结果冲突；
- 产生新的机制或可复用产物；
- 关键实验失败且失败原因已明确；
- 一批低成本检查完成，方向选择可以改变；
- 写作线发现主张缺少支撑；
- 用户主动要求扩大、停止、复核或综合。

触发只提交发生变化的材料和引用。首席模型可以直接读取需要的原文、代码和产物，不依赖永久摘要替代原始证据。

### 6.3 共享准备与执行隔离

多个分支可以共享已经完成的只读材料、环境准备、基线对象和数据索引，但不能共享未声明的可变执行现场。每条分支保留自己的代码改动、参数和输出，避免相互污染。

同一 Agent 可以生成和管理一批普通实验作业，不要求每个随机种子或参数组合都创建一个完整 Thread。只有需要判断、改写、解释或升级时才继续调用模型。

### 6.4 取消、等待与失败

等待资源、等待依赖和等待用户输入都是正常状态，不代表失败。等待中的父线可以继续处理其他分支，依赖完成后再恢复。

取消要停止真实运行、释放对应写者和资源，但已经生成的观察和产物继续可读。工程失败、环境失败、数据失败、科学结果不支持和用户取消分别表达，不能统一成“实验失败”。

## 7. 研究上下文与共享状态

### 7.1 活跃问题状态

集群需要一个持续更新的活跃问题状态，但它不是要求用户维护的数据库表。它由 Host 和首席模型共同维护，面向下一次判断提供：

- 当前问题和约束；
- 已出现的现象；
- 仍在竞争的解释；
- 关键材料和结果引用；
- 分支之间的冲突和共同支持；
- 当前正在执行和等待的行动；
- 下一步可选择的方向。

该状态是可重建的视图。原始会话、工具结果、文件版本、实验输出和来源仍是事实依据，摘要过期不能覆盖它们。

### 7.2 分支回传格式

分支完成一个有意义的推进后，Host 生成紧凑更新：

```text
新发现：改变了什么
影响：涉及哪个问题或假设
依据：原文、文件、运行或产物引用
替代解释：仍可能是什么
下一步：可以继续做什么
```

这是机器间的交接协议，不是用户填写的报告。没有新判断变化的普通进度停留在分支 UI，不进入首席模型上下文。

### 7.3 上下文过期与继续工作

Thread 保留分支身份和成果，Run 只保留本次执行的模型、工具和输入。继续同一工作时可以使用已有的有效上下文；背景大部分过期时用 fresh 输入重建，不把旧对话整段塞回模型。

已有文件、结果和原始材料通过 WorkingState、Artifact 和授权 history 读取。普通消息不能代替文件集成或产物发布。

## 8. 科研严谨性的位置

严谨性不作为前台流程门槛，而作为集群运行时的事实基础：

- Agent 读取的材料保留来源和修订；
- 真实运行保留输入、代码、环境、参数和输出；
- 生成的文件和图表绑定实际内容对象；
- 关键结论可以展开到具体原文、日志或运行；
- 失败、缺失、冲突和未验证状态不被改写成成功；
- 结果进入父线时保留分支和基线关系。

证据表、实验协议、Research Diff 和复现包都是按需生成的产品视图。用户不需要先填写它们，系统也不因缺少某个字段阻止探索。需要交接、发布或集中复核时，首席模型可以从已有轨迹生成这些视图。

## 9. 写作与研究主线

写作不是所有实验结束后的附加功能。写作线持续维护候选主论点和文章结构，但允许随着结果改变方向。

它负责发现：

- 当前结果能支撑什么主张；
- 贡献究竟是性能、机制、适用边界还是新的问题；
- 哪个结论缺少对照、反例或机制解释；
- 哪些图表不能支持当前叙事。

发现论证缺口时，写作线向首席模型提交新的研究请求。强模型负责整体论证和贡献定位，其他模型可以负责局部章节、图表说明、文献整理和格式处理；数字和图表必须来自真实材料与运行结果。

## 10. 用户体验

科研 Profile 的主页面首先展示研究推进，而不是资料管理：

- 当前问题和首席模型的暂时判断；
- 活跃研究路线及其新发现；
- 正在运行、等待或卡住的分支；
- 影响整体判断的异常、冲突和结果；
- 下一轮准备投入的模型和计算资源；
- 当前可以表达的结论与尚未解决的缺口。

文献、代码、数据、日志和图表在需要时从结果卡片展开。用户可以直接用自然语言控制集群，例如：

- “再找一个完全不同的解释。”
- “先停止新增实验，把目前结果综合一下。”
- “这个方向交给更强的模型重新设计。”
- “只运行不需要 GPU 的验证。”
- “把这个结果整理成文章的结果部分，并列出还缺什么。”

页面可以提供来源、实验、产物和文章视图，但它们共享同一研究状态，不分别维护一套数据。默认不展示巨大关系图，不要求用户先填完整问题模板，也不为每个工具调用弹确认。

## 11. 通用内核与领域扩展

通用性来自共享的研究动作和运行时，不来自预先写死所有学科的对象表。

### 11.1 内核保持不变的部分

- Pi Agent loop、Thread/Run、上下文和消息；
- 文件、文档、终端、Web、检索和权限；
- 工作状态、分支、对象、恢复和资源调度；
- 研究分支创建、等待、取消、派生和结果交付；
- 原始材料、运行产物和来源引用；
- 首席模型综合和写作回流的事件接缝。

### 11.2 Profile 和 Adapter 变化的部分

领域 Profile 可以声明：

- 专用数据格式和材料连接器；
- 领域工具、模拟器、实验设备或远程计算；
- 适用的表示、指标和比较方法；
- 领域检索源和引用规则；
- 领域特有的检查器和写作模板。

第一阶段从代码、数据和计算实验开始，是因为它们已经由 Piarium 的文件、Shell、Thread、检索和 Rust kernel 覆盖。这个起点不把产品锁成论文复现工具；后续的生物、材料、物理或实验室适配器应接入同一研究集群，而不是复制一套 Agent 生命周期。

### 11.3 不建设的内容

当前不把以下内容作为科研 Profile 的前置：

- 第二套 Agent loop 或独立的多 Agent 平台；
- 必须填写的科研数据库和固定工作流；
- 一开始就建设全领域文献数据库；
- 自有基础模型、GPU 云或实验室信息系统；
- 用大量自动生成假设替代真实验证；
- 固定数量的假设、实验、审查轮次或 token/墙钟硬门槛；
- 默认常驻的管理层 Agent、群聊或 planner 层。

## 12. 第一条完整纵切

第一条纵切采用一个开放的计算研究问题，而不是只演示资料整理：

> 用户给出一个异常、目标和已有材料；Piarium 并行提出不同解释，检索文献与代码，设计区分性检查，交给快速执行组运行，再由强模型综合结果并决定下一轮。

例如用户提出“这个模型在一批样本上表现异常，找出可能原因并验证”。交付结果应包括：

1. 不同研究路线和它们关注的机制；
2. 已实际执行的低成本检查和运行结果；
3. 被排除、保留或改变的解释；
4. 仍然冲突或缺少依据的地方；
5. 下一轮最值得投入的行动；
6. 可以继续扩展成文章论证的研究备忘录。

论文复现、受控变体和完整复现包是其中一种重要场景，但不定义整个产品。

## 13. 实施顺序与验收

### 13.1 设计阶段之后的第一批能力

1. 研究 Profile 和首席研究主线，复用现有 Pi session 与 Harness；
2. 研究分支 manifest、能力路由和模型动态升级；
3. 调查、设计、执行、复核四类默认任务接缝；
4. 分支增量交接、事件触发综合和同根资源调度；
5. Python/Notebook 或现有 Shell 计算路径的研究运行适配；
6. 研究状态和分支矩阵的最小 UI 投影；
7. 写作线对论证缺口的回流；
8. 用一条开放问题纵切验证并行研究是否真正减少了达到下一步判断的时间。

### 13.2 第一阶段不要求

- 所有领域都能使用；
- 完整实验室设备接入；
- 自动生成完整论文并可直接投稿；
- 真实付费模型质量或科学发现能力的先验保证；
- 固定的 Agent 数量、实验轮数或评测分数；
- 为研究对象另建一套存储和恢复后端。

### 13.3 验收重点

第一阶段应观察真实研究任务中的：

- 首次提出有价值研究方向所需时间；
- 并行分支是否减少了重复探索；
- 低成本执行结果是否能改变后续方向；
- 失败能否区分为工程问题、数据问题和科学结果；
- 强模型是否看到了关键原始材料而非只有下级摘要；
- 研究者是否能随时介入、改方向和继续分支；
- 最终备忘录和文章主线是否减少人工搬运。

比较对象可以是最强单 Agent、异构模型串行协作和异构模型并行协作，在相近资源和时间条件下比较研究进展、有效实验、结论质量和人工返工。调用数、线程数和生成字数不作为成功指标。
