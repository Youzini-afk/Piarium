# Piarium 科研集群设计

Status: accepted design (D-291/D-297, revised by D-300); 7A and the first 7B capability-routing slice implemented at D-298/D-299; remaining stages, including the revised execution and collaboration design, pending

Last updated: 2026-09-19

本文定义 Piarium AI4S（AI for Science）方向的产品中心、研究集群协作形态和第一阶段实施边界。
它建立在现有 Piarium Agent Harness、Thread/Run、Rust kernel、检索、上下文和权限能力之上，不另建一套
Agent runtime、文件权威或持久化系统。当前交付状态仍以 [agent-harness-status.md](agent-harness-status.md)
为准；本文中的“应当”描述目标设计，不能当作已经接线。

## 1. 产品判断

科研工作的主要瓶颈不是把过程整理成足够多的记录，而是研究者能否更快地：

- 发现值得追查的问题；
- 建立跨文献、数据和代码的理解；
- 提出互相竞争的解释；
- 设计能够区分这些解释的行动；
- 把想法快速变成计算、模拟或数据分析；
- 从异常和负结果中发现下一轮问题；
- 形成能支撑结论和文章的整体论证。

证据、版本、运行记录和复现是保证判断不失真的手段。它们必须存在，但不应成为用户开始研究前必须维护的表单，也不应成为产品前台的中心。

Piarium 的科研方向因此定义为：

> **一个由异构模型和计算资源组成、能够并行发现问题、设计实验、快速执行并持续综合的科学研究集群。**

用户面对一条首席研究主线，主线按需要派生多个独立研究分支。强模型负责问题发现、第一性原理分析和综合判断；不同能力的模型负责文献调查、实验设计、实现、监查和复核；Host 调度模型和实际计算资源，Thread/Run 承载分支生命周期。

科研工作的严谨性沉到系统内部：真实输入、运行、输出、引用和版本自动留下可回看的来源。前台首先呈现研究路线、重要新现象、分支卡点和下一步投入方向。

产品形态分成两个独立维度（D-297）：**科研工作台**提供完整的科研 UIUX，**科研工作侧重**组织 Agent 的提示词、
默认激活能力、工具集合与协作方式。工作台由用户主动选择；项目可以提供新对话的侧重默认值，对话可以单独选择侧重。
用户可以在 IDE 中继续科研任务，也可以在科研工作台中处理普通编程对话。切换界面、打开项目或浏览对话都不隐式改变执行配置。

## 2. 第一性原理

### 2.1 科研的基本循环

科研不是“填写计划、执行实验、提交报告”的固定流程，而是对不确定问题持续做有区分力的行动：

```text
问题或异常
  ↓
对现象的暂时理解
  ↓
多个可能解释
  ↓
能区分解释的观察、检索或实验
  ↓
真实执行与结果
  ↓
更新理解，派生下一轮问题
```

一个分支早就有新发现时可以立即派生下一步，另一个分支仍在准备环境，第三个分支可以暂停或转向。研究集群不等待一批任务全部结束后才综合。

### 2.2 AI 的优势与人的职责

模型的优势是同时阅读大量材料、从不同角度提出候选解释、快速生成实现和处理多条反馈。研究者掌握问题价值、领域目标、资源取舍和最终判断，也可以随时改变方向。

Piarium 不把模型的数量或排名当成科学证明。模型之间的独立意见用于扩大探索和暴露冲突；结论仍必须回到实际材料、运行和可解释的观察。

### 2.3 研究效率的定义

集群效率不是调用了多少 Agent，也不是并发数最大。它是单位时间和资源内带来了多少新的研究进展，包括：

- 找到新的问题或机制；
- 排除错误方向；
- 产生可重复的异常或结果；
- 形成更好的下一步实验；
- 让结论或文章论证前进。

没有必要启动 Agent 的批处理、编译、指标收集和进程监控由程序直接完成。模型只在需要理解、选择、改写或解释时介入。

## 3. 产品形态：一条主线与多条研究分支

### 3.1 首席研究主线

用户看到的是一条持续推进整体问题的主线。首席模型负责：

1. 把用户的模糊描述还原成待研究的问题和约束；
2. 发现不同的解释框架和相互竞争的假设；
3. 决定哪些方向值得并行探索；
4. 把分支结果放在一起寻找新关系、冲突和反例；
5. 决定继续、收缩、合并、升级模型或重新定义问题；
6. 形成当前结论、研究备忘录和文章主线。

首席模型不负责轮询进程、搬运每条日志或亲自实现所有代码。普通状态变化由程序记录和展示。
是否需要讨论、复核或综合，由用户或正在工作的 Agent 判断并发起；显式等待的结果可以恢复原有工作。
Host 不凭“异常”“有新产物”之类的事件标签自动开启一次强模型调用。

### 3.2 研究分支

一个分支代表一条独立的研究路线、解释、实验设计或实现路径。任务用自然语言说明要弄清什么，并带上需要的材料引用。
Host 从真实 dispatch、Run 和工具事件记录模型、权限、工作状态、运行与产物身份；观察意味着什么、下一步怎么做，仍由模型判断。
这些判断可以写在正常输出或定向消息中，不要求额外填写“发现、影响、替代解释、下一步”的交接表。
其他 Agent 先看到简短的来源摘录，需要时再读取原始对话、文件和结果，不把整个分支对话灌入父上下文。

### 3.3 Thread 与 Run 的对应

沿用现有 Thread/Run 契约：

- **Thread** 是可以长期继续的研究分支，保留工作身份、成果和关系；
- **Run** 是该分支的一次具体推进，冻结本次模型、工具、权限、范围、输入来源和工作状态；
- 同一 Thread 可以从快速调查切换到强模型解释，再切换到实现或复核，而不丢失已有成果；
- 过期背景可以 fresh 重建输入，工作成果和历史引用继续保留；
- 文件变化、实验产物和分支结果通过现有 WorkingState/Integration 进入父线，普通消息不冒充代码同步。

Thread 树负责谁派发了谁、责任、取消、等待和资源归属；交流不必逐层中转。
授权范围内的父子和同组分支可以相互发送消息、提问和回答。通信不改变树上的生命周期责任，也不自动授予文件、全文读取或控制权限。

## 4. 异构模型与职责

模型槽位按能力配置，不能把产品逻辑永久绑定到某个型号。Astra、肥波、Sol、Opus、Flash 可以作为用户当前的候选绑定，但同一能力在不同 provider 下可以替换。

| 能力 | 典型职责 | 动态升级或改派条件 |
| --- | --- | --- |
| `frontier-reasoning` | 问题发现、第一性原理分析、跨分支综合、核心论证 | 分支冲突、重大异常、研究方向改变、文章论证缺口 |
| `deep-design` | 关键文献深读、机制解释、实验设计、混淆变量分析 | 理论冲突、实验成本高、结果难以解释 |
| `high-throughput-execution` | 实现代码、环境处理、批量分析、普通结果解读 | 重复失败、复杂算法、异常结果 |
| `fast-exploration` | 术语扩展、局部假设、反例、低成本变体、快速检索 | 局部结果影响主方向或需要深度综合 |
| `critical-review` | 独立复核关键实现、方法、异常优异结果和主张 | 只对高影响或有冲突的结果调用 |
| `scientific-writing` | 组织结果、维护候选贡献、暴露论证缺口 | 发现无法由现有结果支撑的主张 |

模型角色是默认路由，分支可以按结果升级、降级或更换模型。快模型不只做工人，也可以大量提出局部想法；强模型不只做主管，也可以直接参与关键实现。普通批处理和日志监查优先由程序完成，Flash 在异常解释和快速修复时介入。

## 5. 默认研究循环

一次研究推进按以下形态运行，不要求所有项目经过相同数量的阶段：

1. 用户给出问题、已有材料和可用资源，首席模型形成初始理解；
2. 按不同解释框架派生若干独立调查或设计分支；
3. 文献、代码、数据和轨迹调查持续为这些分支提供输入；
4. 分支设计低成本且区分力强的检查，执行组批量实现和运行；
5. 程序保留运行和产物，分支按实际需要互相讨论结果、异常和冲突，不等待全部分支结束；
6. 首席模型综合分支之间的新关系，淘汰、合并、升级或派生方向；
7. 研究写作线维护当前可表达的论点，发现论证缺口时重新派发调查或实验；
8. 用户随时可以改变目标、停止方向、扩大路线或要求集中综合。

### 5.1 动态矩阵

研究矩阵可以同时包含不同假设、机制、方法、条件和验证成本，但不一次展开全部组合。每个方向先获得能区分它与其他方向的低成本行动，再根据结果追加资源。

资源分配保留两类投入：

- 继续推进已经出现信号的方向；
- 保留尚未确定但具有独特解释力的方向，避免所有资源只追逐容易产生数字的路线。

代码实现失败不等于假设失败，低成本试验没有信号也不自动等于方向无价值。程序提供退出码、信号、资源不足、连接状态和日志等可观察事实；
失败究竟来自实现、环境、数据还是科学假设，需要模型或研究者结合材料判断，不能靠退出码或关键词替代。

## 6. 实验执行与资源协作

### 6.1 要管理的是持续存在的实验现场

7D 的目标是让 Agent 和研究者能提交、查看、控制、继续并比较实际实验，在本机、远程机器和已有集群之间使用同一套工作方式。
运行不能依赖一个聊天回合或 SSH 窗口一直开着；进程还在运行、机器暂时失联、结果尚未取回必须分别可见。

| 对象 | 用途 | 与已有对象的关系 |
| --- | --- | --- |
| 实验规格 | 命令、代码修订、输入数据、环境、参数、资源要求与输出位置 | 是可复用的执行输入，保存在现有 catalog/对象域；不要求模型填写庞大的通用表单 |
| 执行尝试（attempt） | 一次真实提交及其准备、运行、停止和收集过程 | 绑定发起者 Thread/Run；重试生成新 attempt，并保留原尝试 |
| 后端作业 | 实际进程组或集群调度器的 job | 以目标机器、执行实例和后端 job 身份追踪，不能只保存可复用的 PID |
| 资源分配 | 这次执行实际获得的 CPU、内存、GPU、工作目录或集群 allocation | 请求不等于承诺；已有调度器管理的资源由它确认 |
| 观察与产物 | 日志、指标、退出事实、检查点、图表和结果文件 | 使用现有输出游标、Artifact 与引用保留机制 |

Agent Run 与实验 attempt 不是同一个生命周期。Agent 可以提交一批作业后转去调查；模型等待时让出模型名额，实验仍继续占用自己的计算资源。
改变实验配置后重跑与恢复某个真实检查点分别表达，不把新进程冒充旧实验的连续执行。

### 6.2 面向 Agent 的工具与渐进式披露

模型初始只需要知道如何启动、查看、等待和控制实验，以及如何查看机器资源。常用启动输入是命令、工作分支和必要的资源要求；
环境、目标机器、参数和数据引用可以沿任务已有配置解析，缺少会改变执行结果的信息才要求补充。工具返回解析后的实际目标与配置。

先给简短作业列表：名称、状态、目标、关键进展和结果入口。按 job/attempt 身份继续读取完整配置、日志页、指标、资源分配和产物；
不在每次状态查询中返回全部环境变量、完整日志或所有机器明细。高级控制在目标后端的能力说明中展开，包括输入、信号、检查点或恢复。
现有 shell/进程工具仍服务交互排查；实验管理增加持久身份和批量组织，不再复制一套 Shell。

等待采用事件通知和输出游标，不要求模型循环调用查询。暂停、恢复、调整资源是否可用，取决于后端和实验本身；
暂停进程通常仍持有内存和 GPU，只有观察到资源真正释放后才可重新分配。没有检查点接口的任意脚本不能显示“可恢复训练”。

### 6.3 本机、远程机器与已有集群

- **本机**：继续由私有 Rust kernel 的进程、文件、对象和资源服务执行，Host 负责权限、编排与展示。
- **远程机器**：沿现有远程连接和凭据管理建立目标身份；SSH 用于接入、部署受管执行组件、隧道和必要的排查。
  正式受管实验由远端复用 Rust 进程核心的执行组件或已有 Piarium Host 监督，持久保存 attempt、作业身份与输出游标。
  连接断开后作业继续由远端监督，重连先对账，不能因为没收到启动响应就重复提交。
- **已有计算集群**：通过适配器提交原生作业，首个目标是 Slurm。队列、allocation、抢占和后端终态由原生调度器负责，
  Piarium 保存对应关系并提供统一查看和控制，不能绕过集群规则自行抢卡。Kubernetes Job、Ray Jobs 等按真实部署需求接入，
  不要求用户先安装这些系统才能运行本机或 SSH 实验。

用户可以授权 Agent 在远端查看文件、准备环境、编辑代码和运行排查命令。每次操作绑定可见的目标、路径与权限，
利用已有工具的目标上下文，凭据留在可信 Host；获得一个 job 的查看权不自动获得整台机器的写权限。
受管作业的输入/输出和排查操作的工作目录一致可定位，不能让 Agent 误以为命令仍在本地执行。

仅能使用普通 SSH 的目标也可执行命令，但必须如实说明监督、重连和取消能力；它不能冒充已经具备完整恢复能力的受管后端。
7D 的远程验收要覆盖受管执行路径，不能用一次 SSH 成功打印输出代替。

### 6.4 多机器资源如何分配

资源视图区分四件事：机器容量、已承诺的分配、当前观测用量、用户或集群已有策略。
CPU/内存、GPU/显存、磁盘、数据位置和当前作业来自实际目标或调度器，并带上采样时间、来源与连接状态；
读不到的数值标未知，不能当作零占用。GPU 利用率暂时低也不代表可用，已有 allocation、显存占用和准备中的作业都可能占据资源。

Host 协调器按能力、需求、数据位置、授权和既有优先级选择候选；实际受管资源的分配在其唯一管理方原子确认。
同一设备在多个根任务之间共用一份分配事实，不以“每个主线都看见空闲”作为启动依据。
专用受管机器可由执行组件落实分配；多人共用但没有统一调度器的机器只能报告观察与 Piarium 自己的预留，
不能承诺隔离其他用户进程。用户可选择共享，或使用原生调度器提供真正的资源隔离。

资源不足进入明确队列，模型限流、CPU/GPU、网络和工作区写者分别等待。取消、断连或 Host 重启后先确认实际作业再释放承诺，
不让新任务覆盖仍运行的旧任务；目标失联时展示待对账状态，不凭本地超时判定实验已停止。
公平性沿用部署策略和用户优先级，不新增没有依据的全局配额，也不自动抢占其他人的任务。

研究优先级可以由主线决定；规模或权衡需要时，也可以派一个普通资源协调 Thread，读取同样的资源工具，讨论如何分配。
这个 Agent 负责“哪项研究值得先跑、是否接受较慢机器”等判断，不能绕过资源确认、权限或取消规则。
没有协调 Agent 时系统仍能按已有策略正常排队执行，不为每次资源采样或作业结束调用管理模型。

### 6.5 稳定执行、材料共享与失败

提交先保存 intent 和 attempt 身份，再对后端启动；响应丢失时按该身份查询，确认未创建才重新提交。
停止请求与已停止分开：后端确认整个受管进程组或作业结束后才释放资源；控制进程重启后仍能读取已有日志、作业与产物。
退出事实、连接状态和产物收集状态分别保存，避免“实验结束但复制图表失败”被误记成实验本身失败。

代码修订、数据引用、环境来源和参数在提交时固定。只读数据、已准备环境和基线可以共享，
每个 attempt 的可写目录和输出独立；跨机器传输按内容身份复用，不能每个变体重新上传整套数据。
大日志按页读取；大数据可以保留在远端并记录位置、版本、保留责任和可访问性，按需收集，不能把临时路径伪装成已耐久发布的 Artifact。

普通参数矩阵由程序展开为作业，可以批量等待、取消和对比，不为每个 seed 创建 LLM 会话。
程序记录运行故障的事实；Agent 结合日志解释原因、调整实现或讨论科学含义。持久 Python/Notebook 可后续接入，
但进程内存不等于可复现成果，保留结果与恢复能力仍需实际支持。

## 7. 通用多 Agent 交流与持续现状

### 7.1 自然语言交流

7E 强化整个 Harness 的多 Agent 能力，编程、科研和未来办公使用同一机制。Agent 可向父线提问，父线可以追问子线，
有授权的兄弟或相关分支可以直接讨论、提供材料和互相纠正；不增加固定“首席—设计—执行”的通信层级。

沿现有 `send` / `wait` / `threads` / `read_thread` 演进。发送工具以“发给谁、说什么、是否等待”为核心，例如：

```text
send(to="branch-b", message="这个异常会不会来自归一化？请对照运行 17 的日志。", wait=30)
```

`wait=0` 立即返回投递回执，正值表示最多等待相应秒数，有回复便提前返回。等待超时只结束本次等待，
消息仍有效、对方可以继续处理；发送方可用同一回执继续等或读，不必重复发送。异步发送同样可以提出需要处理的问题，
不能把“不等回复”解释成“对方不得执行”。具体工具 schema 随生产改造统一替换，当前已交付接口不因此自动获得此参数。

消息内容自由，不要求填写发现类型、影响、替代解释、优先级或下一步。发送身份、messageId、幂等请求、时间和回复关联由 Host 的耐久消息账本承载；
正常答复沿当前收到的消息上下文关联，多问题同时存在时可使用简短消息引用明确回复哪条，不把任何不相关输出当作答复。
自然语言中的引用按原有工具权限读取，发送消息本身不扩大对方的文件或来源权限。

### 7.2 投递、等待与继续执行

发送方是否等待与接收方如何执行是两个问题。运行中的目标在下一安全输入切点收到消息；
正在等待且可恢复的目标可由发给它的消息恢复工作；空闲的可继续 Thread 收到明确请求时沿现有准入启动新 Run。
已归档、已删除或不可用的目标返回真实状态，不自动复活已终止任务。消息和回复保留在账本中，重连不重复投递或启动。

等待让出模型执行名额，不持有阻止收件、回复或取消的生命周期锁。答复先于等待注册到达，也必须能被取到；
发送方取消等待不删除已发送消息。相互提问时允许在安全切点继续收件和处理，不能让两个等待动作堵住通信。
必要的准入仍使用已有模型与权限机制，不额外添加通用通信轮数或消息频率硬限制。

Host 只按显式交流、用户请求和已建立的等待/订阅继续工作。实验完成可以满足 Agent 已发起的等待，
文件变化、普通心跳或关键字不自动派发强模型综合。收到回复不自动回复确认或感谢，不建立系统生成的回复循环。
科学冲突是否需要更强模型，由读到材料的 Agent 或用户决定。

### 7.3 自动生成的简短现状表

Agent 在工作过程中持续得到当前团队的简短现状。默认表只保留四列：

| 线程 | 任务 | 状态 | 进展 |
| --- | --- | --- | --- |
| 分支 A | 查归一化差异 | 工作中 | 已定位到训练与验证的归一化差异… |
| 分支 B | 跑对照实验 | 等待作业 | 对照组已提交到远程机器… · 新结果 |
| 分支 C | 解释异常 | 已完成 | 异常集中在低样本类别… · 新消息 |

“任务”来自已有任务 brief，“状态”来自真实 Thread/Run/等待事实。
“进展”由程序摘取该 Agent **最近一段已完成的可见文字输出**，包括工作中的普通说明和最终答复，
按约 20 个可见字符截断并加省略号。这里是展示长度，不限制原文、消息长度或模型输出；不抓取不可见推理。
不要求 Agent 另行发布近况、调用状态工具、写特殊标签，也不运行总结模型。

最近变化、新消息和新结果合并到“进展”这一列，以短标记或带来源的摘录提示。收到别人的消息不能冒充该线程自己的判断。
截取只做确定性文本整理，不判断哪句话更重要，不把模型措辞变成 Host 已验证的事实。
无新文字时保留带时间的旧摘录或显示暂无；新的 Run 不把旧 Run 的结论伪装成刚产生的进展。

每条摘录关联实际 Thread/Run、原文 entry/block、修订和时间。`read_thread` 可直接展开对应原段落，
再按需查看邻近上下文、新消息、结果和日志；即使该线程随后继续输出，仍能定位表中当时引用的内容。
首次阅读不必加载所有细节，读取表和原文也不会唤醒被查看的 Agent。

### 7.4 持续更新与 Zone 2

Host 用已有输出、消息、Run 和结果事件维护可重建投影。流式输出在段落完成、工具边界或最终完成后发布可引用修订，
不逐 token 改表，也不轮询模型索取状态。UI 可以消费这些变化；模型只在下一次实际请求模型前拿到更新。

初次输入给短表，随后在 Zone 2 追加发生变化的行和必要的移除说明，未变化的行不重复追加。
这覆盖同一次 Agent 工作中的工具续接与等待返回，不能只在初始化或新用户回合注入；
要接入真正的模型输入准备切点，而非假定一次 `before_agent_start` 就覆盖整个工具循环。
已经发出的请求和已有前缀保持不动，保留缓存优先的上下文设计。

观察游标按实际接收者分开，UI 展开不代替模型看过。仅准备、过滤或发送失败不确认已交付；
压缩/fresh 后检查对应原文收据是否仍保留，缺少时重建必要现状，不能一律清零后重复注入全部历史。
团队变大时默认围绕当前根、关系和正在关注的分支展开，明确提示还有哪些范围可查询，不设固定线程数量截断后假装全貌。

### 7.5 研究理解与原始材料

程序能够维护任务、状态、原文摘录和引用，不能从这些机械推导“假设已被支持”或“值得停止某方向”。
研究备忘录、解释对比、当前论点和文章结构由 Agent 在需要时写作并保留来源；可以在工作台查看，
但不设置必须持续更新的 `ResearchBoard` 或强制研究交接格式作为交流前置。

Thread 保留身份和成果；上下文有效时 continue，大部分过期时 fresh，以当前任务和原始引用重建输入。
沿 D-284/D-286 的容量与续接机制，不为现状表再启动 keeper。文件、结果和材料仍经 WorkingState、Artifact 和授权 history 读取，
消息与摘录都不能代替文件集成或结果发布。

## 8. 科研严谨性的位置

严谨性不作为前台流程门槛，而作为集群运行时的事实基础：

- Agent 读取的材料保留来源和修订；
- 真实运行保留输入、代码、环境、参数和输出；
- 生成的文件和图表绑定实际内容对象；
- 关键结论可以展开到具体原文、日志或运行；
- 失败、缺失、冲突和未验证状态不被改写成成功；
- 结果进入父线时保留分支和基线关系。

证据表、实验协议、Research Diff 和复现包都是按需生成的产品视图。用户不需要先填写它们，系统也不因缺少某个字段阻止探索。需要交接、发布或集中复核时，首席模型可以从已有轨迹生成这些视图。

## 9. 写作与研究主线

写作不是所有实验结束后的附加功能。写作线持续维护候选主论点和文章结构，但允许随着结果改变方向。

它负责发现：

- 当前结果能支撑什么主张；
- 贡献究竟是性能、机制、适用边界还是新的问题；
- 哪个结论缺少对照、反例或机制解释；
- 哪些图表不能支持当前叙事。

发现论证缺口时，写作线用同一个 `send` 自然说明问题和材料，可以询问首席，也可以直接找有授权的调查或实验分支讨论，按需要等待回复。
不增加专用 `writing-gap` 表单或自动唤醒链。强模型负责整体论证和贡献定位，其他模型可以负责局部章节、图表说明、文献整理和格式处理；数字和图表必须来自真实材料与运行结果。

## 10. 产品入口、工作台与工作侧重

### 10.1 两种选择分别负责什么

| 选择 | 产品入口 | 影响 | 权威与保留范围 |
| --- | --- | --- | --- |
| 工作台 UIUX（Workbench Profile） | 现有 Agent/IDE 切换区域新增工作台入口 | 完整 Shell、导航、布局、信息呈现、操作方式与切换动画 | 复用现有工作台选择与 Shell 生命周期；共享会话、文件、编辑器、任务和产物 |
| 项目默认工作侧重 | 项目设置 | 为新对话提供 Agent 工作方式的默认选择 | 复用项目设置；创建对话时捕获，不持续覆盖已有对话 |
| 对话工作侧重（Agent Profile） | 对话内明确、可见的侧重控件 | 提示词、默认激活能力、工具组织、上下文与协作策略 | 复用会话配置和 Run/worker 配置世代；对话手动选择优先 |

Workbench Profile 与 Agent Profile 在命名、存储字段和消费者中保持不同身份。后者的用户可见名称是“工作侧重”；
本文不再用未限定的“科研模式”或“research Profile”同时指代两者。IDE 保持完整开发环境的定位，包含编辑、调试、
运行和工程管理。科研工作侧重可以使用这些能力，不要求用户离开 IDE 才能进行科研。

### 10.2 主动切换整套 UIUX

科研工作台入口放在现有 Agent/IDE 切换区域，与现有切换入口共同组织；后续办公工作台沿用同一入口机制。
这不是项目选择菜单中的项目类型，也不增加一个独立的“研究中心”导航、研究项目库或平行会话列表。
切换控件改变整套 UIUX，不能只改标题或给现有页面增加一个标签。

切换沿用 [Motion 平台](piarium-motion-platform.md) 的 Transition Scene、遮盖/揭示动画和 Shell 交接，
遵循已有 reduced-motion 偏好与失败恢复。新 Shell 就绪并完成选择提交后揭示目标界面；失败继续保留原工作台。
动画仅服务于前台切换，后台模型请求、实验进程和任务事件照常推进，不为动画重建 Pi 会话或复制 Document 状态。

用户当前选择的工作台独立于项目、会话和工作侧重。打开另一个项目或对话时保持当前工作台，不根据其侧重、
历史使用界面或任务内容自动切 Shell。7A 已移除按 workspace 解析所选 Profile 的路径；
项目可以继续保存面板尺寸、打开的资源等工作现场，不能用这些布局偏好覆盖用户当前选择的工作台。
选择仍由现有工作台配置与 Surface transition controller 管理，不新增另一套科研模式状态。

单纯切换工作台不调用模型、不派发研究、不修改工具/权限/模型绑定，也不应用 Agent 配置预设。
同一个正在运行的研究在 Agent、IDE、科研工作台中沿同一 Thread/Run 展示；视图挂载不创建新的研究根。

### 10.3 工作侧重的继承与执行时机

1. 新对话采用用户在创建时明确选择的侧重；没有覆盖时捕获项目默认值，再没有则使用现有通用/编程默认。
   当前工作台不参与这条解析链。在科研工作台中新建对话也不暗中强制科研侧重。
2. 对话保存自身的侧重选择及来源，输入区域能看见当前侧重。修改项目默认只影响之后创建的对话，
   已有对话保持自身配置；用户可以在当前对话明确应用另一侧重或当前项目默认。
3. 对话中修改侧重作为待应用配置，从下一次新 Run 启动前的安全切点生效；正在执行的 Run 内，steer 和 followUp 队列继续使用原侧重。
   当前执行和已经派发的分支保持启动时的模型、工具、权限、输入与侧重修订；需要新 Run 时沿同一 Thread 建立。
   新配置准备失败时保留原配置并显示实际失败，不能显示已应用却仍执行旧配置。
4. 侧重选择和研究任务生命周期分开。离开科研侧重不删除研究成果，也不隐式取消在途分支；停止、暂停和继续仍用现有任务动作。
   再次继续科研时绑定已有研究主线，不能因切回侧重重复创建研究根或派发任务。
5. 工作侧重决定默认启用哪些已安装能力及其组织方式，不把领域变成权限围栏。科研可以编程，办公可以做数据分析；
   实际权限仍由用户授权和 Host 执行，模型分工沿用户模型槽位解析，侧重不扩大授权或复制凭据。

未来办公工作台与文件知识工作侧重采用同样的分离。此阶段先交付科研的实际消费者，不预建尚无用途的办公工具或另一套 Profile 框架。

### 10.4 科研工作台中的研究推进

科研工作台提供自己的信息组织与交互，主页面首先展示研究推进：

- 当前问题和首席模型的暂时判断；
- 活跃研究路线及自动摘取的最近输出，按需展开全文；
- 正在运行、等待或卡住的分支；
- Agent 实际讨论的异常、冲突和结果，而非程序推断的研究结论；
- 下一轮准备投入的模型和计算资源；
- 当前可以表达的结论与尚未解决的缺口。

文献、代码、数据、日志和图表在需要时从结果卡片展开。用户可以直接用自然语言控制集群，例如：

- “再找一个完全不同的解释。”
- “先停止新增实验，把目前结果综合一下。”
- “这个方向交给更强的模型重新设计。”
- “只运行不需要 GPU 的验证。”
- “把这个结果整理成文章的结果部分，并列出还缺什么。”

页面可以提供来源、实验、产物和文章视图，但它们共享同一研究状态，不分别维护一套数据。默认不展示巨大关系图，不要求用户先填完整问题模板，也不为每个工具调用弹确认。

主线交流、研究分支与结果是默认视觉重点。文件、Git、原始终端按需要展开；代码可在共享编辑器中修改和调试，
数据、图表、文献与文章可以并排或展开到中央。用户也能主动切到完整 IDE 继续同一任务，切回后保留资源和阅读位置。
这些入口消费既有 Documents、编辑器、进程和 Artifact，不为科研复制 IDE 或另造数据权威。

当当前对话采用普通编程侧重时，科研工作台仍能展示并操作这段对话；没有研究分支或实验结果就如实显示为空，
不能为填充科研面板创建任务。反过来，Agent/IDE 中的科研对话仍能派发、等待、继续分支和读取成果，
专门的研究视图只改善呈现，不是调用科研能力的门槛。

## 11. 通用内核与领域扩展

通用性来自共享的研究动作和运行时，不来自预先写死所有学科的对象表。

### 11.1 内核保持不变的部分

- Pi Agent loop、Thread/Run、上下文和消息；
- 文件、文档、终端、Web、检索和权限；
- 工作状态、分支、对象、恢复和资源调度；
- 研究分支创建、等待、取消、派生和结果交付；
- 原始材料、运行产物和来源引用；
- 自然语言定向交流、按需等待、持续现状与原文展开。

### 11.2 工作侧重和 Adapter 变化的部分

领域 Agent Profile（工作侧重）可以声明：

- 专用数据格式和材料连接器；
- 领域工具、模拟器、实验设备或远程计算；
- 适用的表示、指标和比较方法；
- 领域检索源和引用规则；
- 领域特有的检查器和写作模板。

第一阶段从代码、数据和计算实验开始，是因为它们已经由 Piarium 的文件、Shell、Thread、检索和 Rust kernel 覆盖。这个起点不把产品锁成论文复现工具；后续的生物、材料、物理或实验室适配器应接入同一研究集群，而不是复制一套 Agent 生命周期。

### 11.3 不建设的内容

当前不把以下内容作为科研能力的前置：

- 第二套 Agent loop 或独立的多 Agent 平台；
- 必须填写的科研数据库和固定工作流；
- 一开始就建设全领域文献数据库；
- 自有基础模型、GPU 云或实验室信息系统；
- 用大量自动生成假设替代真实验证；
- 固定数量的假设、实验、审查轮次或 token/墙钟硬门槛；
- 默认常驻的管理层 Agent、强制群聊或 planner 层；确有调配需求时允许派出普通资源协调 Thread。

## 12. 第一条完整纵切

第一条纵切采用一个开放的计算研究问题，而不是只演示资料整理：

> 用户给出一个异常、目标和已有材料；Piarium 并行提出不同解释，检索文献与代码，设计区分性检查，交给快速执行组运行，再由强模型综合结果并决定下一轮。

例如用户提出“这个模型在一批样本上表现异常，找出可能原因并验证”。交付结果应包括：

1. 不同研究路线和它们关注的机制；
2. 已实际执行的低成本检查和运行结果；
3. 被排除、保留或改变的解释；
4. 仍然冲突或缺少依据的地方；
5. 下一轮最值得投入的行动；
6. 可以继续扩展成文章论证的研究备忘录。

论文复现、受控变体和完整复现包是其中一种重要场景，但不定义整个产品。

## 13. 实施顺序与验收

D-292 的 [测试与 CI 体系重整](testing-ci-design.md)（阶段 Q）和 D-296 的旧伴侧插件清理均已完成，
现在进入本节科研功能实施。D-297 补齐工作台与工作侧重的独立选择，D-300 补齐实验执行、远程资源和通用协作设计，
替换机械事件综合及强制交接格式，不增加科研表单、模型质量审批或固定评测分数门槛。
实施沿用 Q 整理后的验证职责，不另建科研专用测试框架；具体交付顺序见 [实施计划](agent-harness-plan.md)。

### 13.1 设计阶段之后的第一批能力

1. 科研工作台入口、整体 UIUX 与既有切换动画，以及独立的项目默认/对话工作侧重，接通真实首席主线；
2. 研究分支 manifest、能力路由和模型动态升级；
3. 调查、设计、执行、复核四类默认任务接缝；
4. 父子与同组 Agent 的自然语言交流、可等待发送、自动现状和原文展开，适用于整个 Harness；
5. 本机与受管远程 batch 执行、多机器资源调度和已有集群接入，持久 Notebook 按后续真实需求接入；
6. 在科研工作台中逐步接通研究状态、分支、实验与成果视图；
7. 写作线对论证缺口的回流；
8. 用一条开放问题纵切验证并行研究是否真正减少了达到下一步判断的时间。

### 13.2 第一阶段不要求

- 所有领域都能使用；
- 完整实验室设备接入；
- 自动生成完整论文并可直接投稿；
- 真实付费模型质量或科学发现能力的先验保证；
- 固定的 Agent 数量、实验轮数或评测分数；
- 为研究对象另建一套存储和恢复后端。

### 13.3 验收重点

第一阶段应观察真实研究任务中的：

- 首次提出有价值研究方向所需时间；
- 并行分支是否减少了重复探索；
- 低成本执行结果是否能改变后续方向；
- 失败能否区分为工程问题、数据问题和科学结果；
- 强模型是否看到了关键原始材料而非只有下级摘要；
- 研究者是否能随时介入、改方向和继续分支；
- 最终备忘录和文章主线是否减少人工搬运；
- 远程失联、恢复和取消是否如实反映作业与资源，而非重复启动或提前释放；
- Agent 能否在持续工作中看见同伴的实际变化并直接交流，无需额外维护状态报告或启动总结模型。

产品交互同时验证：切工作台和浏览项目/对话不改执行配置；IDE 能继续科研任务；科研工作台能处理普通对话；
项目默认不覆盖已有对话；运行中修改侧重只在下一轮应用；失败的工作台切换保持原界面和工作现场。

比较对象可以是最强单 Agent、异构模型串行协作和异构模型并行协作，在相近资源和时间条件下比较研究进展、有效实验、结论质量和人工返工。调用数、线程数和生成字数不作为成功指标。
